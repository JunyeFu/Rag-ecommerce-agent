## 2. 缺陷清单与根因判断

### MIMO-AGENT-001：明确待购写入意图没有产生 `cart.update`

- **等级**：P1，阻断 Agent 写操作闭环。
- **复现**：中度专项 `cart_write`；先提供商品/报价上下文，再要求“以数量 2 加入待购并等待审批”。MiMo 返回合法响应但没有工具调用，执行器没有机会创建审批动作。
- **直接证据**：`actual_tool=null`、`call_count=0`、`expected_tool=cart.update`；同一报告的 `requote` 与 `list_write` 分别成功，说明凭据、端点和基础工具 Schema 并未整体失效。
- **根因置信度**：高（“空工具调用”已确认）；“模型为何拒绝调用”的语义原因未被当前报告记录，不能进一步臆断。
- **代码原因**：`model_provider.py` 对写操作的系统提示使用“可调用”，并允许模型在无工具调用时直接返回 `()`；没有把“已识别的明确写入意图”变成必须选择目标写工具的结构化决策，也没有在空调用时生成可诊断的 `write_intent_unfulfilled` 事件。
- **影响**：真实模型下清单可成功但待购不稳定；审批、幂等和状态持久化虽有测试覆盖，却无法覆盖“规划器不发起写操作”的入口缺陷。
- **修复入口**：收紧写意图契约（目标集合、商品/报价 ID、数量、审批意图）；空工具调用不得静默结束，应返回可诊断的未满足意图状态；增加 MiMo 专项回归，要求 `cart.update` 正确入队且仍由执行器拦截审批。
- **验收**：同一场景单次调用得到 `cart.update`，Schema 100% 合法；审批前状态不变，批准后状态只改变一次，重复批准不重复写入。

### MIMO-EVAL-002：G05 的目录实体被模型判为需要澄清

- **等级**：P1，影响黄金场景通过率。
- **复现**：G05 查询为 `Arc Compute Forge 03 演示电脑`，期望商品 ID 为 `ce106976-76fd-5a1c-8bd2-b4aceb064633`，实际进入 `clarification_required`，没有检索调用。
- **根因置信度**：中。已确认是模型在首轮没有进入检索；尚不能仅凭脱敏报告确定是“用途缺失”触发了系统提示，还是品牌/品类实体识别失败。
- **代码/数据关系**：系统提示要求“商品品类和用途都不明确”时必须澄清；G05 虽给出品牌、型号和品类，但没有用途。其它同样没有用途的 G04/G07 能通过，说明这不是单纯的“缺少用途”必然规则，而是模型对该实体/上下文的决策不稳定。
- **影响**：精确商品查询不能稳定到达 RAG，Agent 失去商品事实与证据链。
- **修复入口**：补充“已知目录实体优先检索”的规划契约与别名/实体命中测试；报告保存首轮决策摘要或有限分类结果，以便区分实体识别失败与澄清策略触发；不得用 fake 结果覆盖真实失败。
- **验收**：G05 及同类精确 SKU 查询先调用 `catalog.search`，无用途时仍可检索；只有缺少检索所需的实体/品类时才澄清。

### MIMO-DATA-003：G08 评测期望与用户输入不一致

- **等级**：P1，评测契约缺陷，不应直接归咎模型。
- **复现**：G08 查询仅为 `Aural Audio Quiet 03 演示耳机`，但 `flow` 声明包含 `requote` 和 `resolve`。模型完成 `search → facts → offers → comparison` 后未调用 `offer.requote`；报告因此将流程判为未完成。
- **根因置信度**：高。
- **证据**：黄金场景文件没有“重新询价、报价过期或刷新链接”的用户意图字段；当前 Provider 提示也只允许在用户明确要求刷新已有报价时调用 `offer.requote`。模型按输入执行只读链路与此契约一致。
- **影响**：测试把未被用户要求的动作当成必需动作，造成假阳性失败，污染模型质量判断。
- **修复入口**：二选一并固定版本：将 G08 查询改为显式“重新核验/刷新报价并解析链接”，或删除 `requote/resolve` 期望并新增独立明确意图场景；禁止仅修改通过阈值掩盖契约不一致。
- **验收**：每个 `flow` 步骤都能从查询或前置事件中找到可审阅的触发条件；缺少触发条件的场景不得进入发布门禁。

### MIMO-EVAL-004：无推荐场景被错误记为证据覆盖 0

- **等级**：P1，评分器缺陷。
- **复现**：`run_real_model_evaluation.py` 当前计算为 `products and len(evidence_refs) >= len(products)`；G05 合法地没有推荐时被记为 `evidence_coverage=0.0`，汇总又取所有场景的最小值，因此即使 10/10 可解析、8/10 流程完成，报告仍因最小覆盖率为 0 判定失败。
- **根因置信度**：高，属于确定的布尔/聚合逻辑问题。
- **影响**：澄清、离线或失败闭环等“不应推荐”的场景无法表达 N/A，导致正式门禁不能区分“无推荐且无伪造”和“推荐无证据”。
- **修复入口**：将覆盖率改为三态（`PASS`、`FAIL`、`NA`）或只在 `recommendations > 0` 的场景上聚合；同时保留“有推荐时 100% 有证据”的门禁。重新生成新 run，不覆盖 run-011 原始结果。
- **验收**：无推荐且无商业事实伪造的澄清场景不因证据覆盖被判错；任何实际推荐缺证据仍为硬失败。

### MIMO-OBS-005：模型空决策与首轮澄清缺少可诊断记录

- **等级**：P1，阻碍根因闭环。
- **复现**：两份报告只记录 `actual_tool`、工具列表、终态和 token；对 `cart_write` 的空工具调用以及 G05 的澄清没有记录模型返回的有限决策摘要、提示版本或分类原因。
- **根因置信度**：高，属于证据结构缺失。
- **影响**：无法区分模型拒绝、模型未理解、工具调用被解析器丢弃或上游响应不完整；修复只能依靠猜测。
- **修复入口**：在不保存密钥和完整敏感原文的前提下，记录 provider 响应状态、是否存在 `tool_calls`、工具名、Schema 解析结果、终态原因和 prompt/eval 版本；空工具调用必须显式标记。
- **验收**：任何“无工具但终止/澄清”的真实 case 都能从报告定位到决策分支；日志不含 API Key、签名口令或本机绝对路径。

## 3. 明确排除的根因

本轮证据不支持以下判断：

- 不是 API Key 或 MiMo 端点整体不可用：同一重度运行有 10/10 可解析结果，且多数场景完成完整只读链路。
- 不是工具 Schema 全局失效：10/10 Schema 合法；`offer.requote`、`list.update` 在专项运行中分别成功。
- 不是执行器绕过审批：本轮未发现未授权写入或导航，且失败发生在工具调用产生之前。
- 不是商业事实伪造：重度与专项结果均未发现 unsupported commercial facts。

## 4. 修复顺序

1. 先修 `MIMO-EVAL-004` 和 `MIMO-DATA-003`，冻结可解释的评测契约，重新生成一份新报告。
2. 再修 `MIMO-AGENT-001`，把明确写入意图变成可验证的结构化规划结果，并保留执行器审批边界。
3. 处理 `MIMO-EVAL-002` 的实体优先检索与澄清规则，使用 G05 及同类 SKU 回归。
4. 最后补 `MIMO-OBS-005`，确保后续真实失败可以直接定位而不是依赖猜测。

在上述缺陷关闭前，真实 MiMo 证据只能标记为“当前 run 失败/待修复”，不得在 README、Release 或求职材料中写成“真实模型门禁已通过”。本文件不包含凭据，也不执行暂存、提交或推送。
