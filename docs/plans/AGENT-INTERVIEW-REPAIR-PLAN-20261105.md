## Q1：为什么采用 Agent，如何保证它终止？

**现状与判断：** 空计划进入澄清；重复已完成工具触发停止；工具失败后放弃计划不会假报完成；九工具计划在执行前被拒绝。当前没有可据此提出的修复项。

- 行动：保留现有 `MAX_TOOLS=8`、`MAX_REPLANS=2` 及写工具审批门禁，不为已通过项增加新状态机、重试或兜底。
- 实施涉及：只有后续修改编排时，才联动 [runtime.py](../../packages/agent-runtime/src/ragcommerce_agent_runtime/runtime.py) 与既有运行时测试。
- 验收：重跑首轮审查中的四个 `test_q1_*`；原有终止原因与事件顺序不变，工具执行次数不超限。
- 关闭条件：本题为“本地已通过，保留回归”。真实模型的任务成功率不能由这四个替身测试推断。

## Q2：混合检索能否同时保证召回与硬约束？

**F05 根因：** `HybridIndex._satisfies` 仅在文档存在该属性时比较取值，属性不存在便跳过。缺少“防水”字段因此可能通过 `防水=IP68` 过滤。API 的严格 IP68 路由正向对照已通过，问题定位在底层过滤器。

- 最小改动：[search.py](../../packages/retrieval/src/ragcommerce_retrieval/search.py) 继续单独处理 `category`、`price_max`、品牌与排除词等保留过滤项；对于普通属性，键缺失直接返回不匹配，存在时沿用当前取值比较规则。
- 保留行为：预算、类目、精确 SKU、排除项不变；不顺带引入属性同义词、模糊等级推断或新召回模型。
- 验收：`test_q2_missing_attribute_does_not_satisfy_explicit_filter` 转绿；同时覆盖属性存在且匹配、存在但不匹配，并保留其余四项 Q2 对照。
- 完成标准：显式属性约束不会因字段缺失而放行；API 仍不宣称缺少证据的严格匹配。只关闭 F05，不把这一修改写成召回率提升。

## Q3：怎样防止价格、库存与商家承诺幻觉，避免越权工具调用？

**F01–F03 共因：** 当前公共自由文本通过价格正则筛选，既把用户预算当成金额事实来源，又漏过多种货币写法和库存、销量、配送、店铺身份、保障承诺。补充几个正则无法建立商业事实边界。工具写入审批对照已经通过。

- 默认方案：在 [runtime.py](../../packages/agent-runtime/src/ragcommerce_agent_runtime/runtime.py) 统一生成公开的阶段说明及澄清提示；根据实际运行状态、已验证的缺失槽位选择固定模板，不直接回显模型给出的说明、推理或用户原文。无法映射槽位时使用固定的补充需求提示。
- 事实呈现：商品、价格、运费及验证状态仍通过现有结构化商品卡和 `OfferQuote` 展示；没有依据的字段保持未知。阶段文本不承载新的商业判断。
- 联动改动：[model_provider.py](../../packages/agent-runtime/src/ragcommerce_agent_runtime/model_provider.py) 停止为这类阶段文本发起响应模型调用；保留模型规划与多模态理解。公共边界放在运行时，替换 provider 也不能绕过它。仅为旧接口保留必要签名，不新增裁判模型或通用事实校验框架。
- 代价：减少自由措辞和一次阶段响应调用，换来可证明的事实来源边界；适合当前“商品卡承载结论、文本只解释阶段”的产品契约。
- 验收：把现有八个失败输入继续送入实际 API，断言公开 MESSAGE 没有预算冒充售价、货币变体、伪造店铺和库存物流承诺；有效报价卡照常展示，审批前写入次数仍为零。补一项替代 provider 注入用例，证明运行时边界生效；传输调用记录证明阶段文本不再请求模型。
- 测试迁移：原审查文件和 JUnit 保留。旧的“provider 必须抛异常”探针若因阶段请求被取消而不再适用，应明确映射到“公开输出安全且不调用该阶段模型”的常规回归，不能仅修改期望值或标记跳过来宣称修复。涉及该阶段的预算测试改在仍实际调用的模型请求边界验证，避免空跑通过。
- 完成标准：F01、F02、F03 同时在公开输出路径关闭；金额预算仍只作约束，工具审批行为不变。不宣称所有提示注入或真实模型失败均被消除。

## Q4：用户隔离是否等同于身份认证，多轮恢复凭什么可信？

**F04 根因：** 开发模式按客户端传入的 `X-User-ID` 识别所有者，只校验 UUID 格式。知道某个 UUID 就能自报身份；这是缺少生产认证，并非绕过了一套已经存在的生产认证。

- 默认方案：当前没有账号体系，采用服务端签发的匿名安装凭据。服务端生成所有者 UUID 和 256 bit 随机不透明令牌，持久层只保存令牌的单向校验值及所有者绑定；客户端以后发送 `Authorization: Bearer …`。安装令牌只授权其自身用户数据，不获得运营管理权限。
- 入口改动：[security.py](../../apps/api/src/ragcommerce_api/security.py)、[app.py](../../apps/api/src/ragcommerce_api/app.py) 统一从验证后的凭据取得所有者。无效或撤销令牌返回 401；已认证的其他所有者访问资源继续返回 404。无效 Bearer 绝不退回 UUID 请求头。
- 数据和客户端：实施包再声明必要的凭据表迁移、签发/撤销接口与测试路径；[CommerceApi.kt](../../apps/android/app/src/main/java/com/ragcommerce/agent/data/remote/CommerceApi.kt) 的普通请求和 SSE 同步使用凭据，并由 Android Keystore 保护本地令牌。实际调用用户接口的其他客户端同样更新，不把令牌放入 URL 或日志。
- 开发数据：UUID 请求头仅保留在显式的本地夹具入口，生产应用工厂不能启用它。不能凭旧 UUID 换取新生产凭据；旧演示数据留在演示域，不自动迁移认领。跨设备账号恢复不属于这次修复。
- 验收：已知所有者 UUID 但无令牌返回 401；伪造、撤销令牌均被拒绝；A 的有效令牌访问 B 的任务/媒体/记忆/删除接口不成功；A 的普通请求和 SSE 正常；重启后合法凭据仍可用。保留同意记忆与幂等体冲突回归，并与 Q10 验证删除后的凭据撤销。
- 完成标准：认证、持久层和 Android 实际请求均验证通过后，才能关闭“可对外开放”的 F04；只做 API TestClient 不能替代客户端或生产配置验收。令牌方案依据 [OWASP 会话管理建议](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

## Q5：怎样证明质量、性能、成本，怎样保证 CI 证据可复现？

**F06 根因：** 既有安全快照记录了本地 CRLF 锁文件的原始字节摘要，Linux/Git LF 字节不同。另一个已观测 CI 失败来自购物车响应增加商品与报价字段后，E2E 仍按旧的两字段对象做全等比较。

- 最小改动：拟新增根目录 `.gitattributes`，只对根目录 `package-lock.json` 和 `uv.lock` 固定 `text eol=lf`；将这两份工作文件写成 LF，按现有 [security_gate.py](../../scripts/security_gate.py) 流程重新生成 [安全快照](../security/evidence/security-gate.json)。不全仓重写换行，不削弱摘要比较，不修改历史证据。
- E2E 同步：[agent-business.spec.ts](../../e2e/agent/agent-business.spec.ts) 按实际购物车契约断言长度、offer ID、数量，以及 `product.product_id`、`quote.offer_id` 和验证/报价关系；不能只把断言放宽成 HTTP 200 或忽略全部新增字段。
- 验收：`test_q5_security_snapshot_matches_git_checkout_bytes` 转绿；相关购物车 E2E 通过；在实际 Linux CI 完整跑完既有 Python、Web、Android、compose-contract 所需检查，不能用本地成功覆盖此前失败及跳过步骤。
- 保留项：真实付费边界必须在调用前预留共享 Token 预算，缺失 usage 不能记零。三项既有付费边界测试继续通过；审查中撤回的“无预算替身漏计”误报不再安排修复。
- 完成标准：锁文件规范字节、安全报告与 CI 结果一致后关闭 F06。既有 182 ms 等指标仍按原测量阶段解释；确定性构造的参考集不升级成真实模型质量，也不因修复 CI 重跑昂贵模型基准。

## Q6：SSE 断开后如何准确恢复，避免事件重复与遗漏？

**现状与判断：** 五项探针均通过，已覆盖精确后缀、无重复 ID、非法/负游标、超前游标、终态及禁缓存响应头。本题没有已复现的代码漏洞。

- 行动：保留 [app.py](../../apps/api/src/ragcommerce_api/app.py) 的游标与回放契约；修改事件模型、Q3 文本或 Q4 鉴权时，重跑全部 `test_q6_*`。
- 验收：事件 ID 单调，恢复返回严格后缀，终态游标不重放旧事件，非法输入保持 400/409，`no-store` 和禁代理缓冲头不回退。
- 边界：受控真实连接断开、代理缓冲以及 Android 重连需在产品集成验收时验证，不能把 TestClient 回放写成移动网络验收。本题不为尚未观察的网络故障预先加重试框架。协议依据 [WHATWG SSE 规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)。

## Q7：索引更新失败时，如何保证旧版本继续可用？

**F07 范围：** 两个夹具构建器会先清空旧状态。当前主链 `QdrantHybridSemanticIndex.build_index` 的失败保留旧别名对照已经通过，不能据此宣称主链也存在同一缺陷。

- 内存夹具：[outbox.py](../../packages/retrieval/src/ragcommerce_retrieval/outbox.py) 的 `OutboxProjector.rebuild` 在独立候选投影中完整排序、校验并回放；全部成功后再一起替换投影、去重和版本状态，失败保留现有对象的可读内容。
- 旧 Qdrant 夹具：[qdrant_projection.py](../../packages/retrieval/src/ragcommerce_retrieval/qdrant_projection.py) 采用候选 collection 完成写入后再原子切换 alias 的流程；失败只清理本次新建候选。与别名同名的既有物理 collection 应明确拒绝破坏性重建，若需迁移另行显式安排。
- 保留主链：[semantic.py](../../packages/retrieval/src/ragcommerce_retrieval/semantic.py) 继续先写候选再切换；只复用必要的发布步骤，不引入另一套索引框架，也不为夹具下载模型。
- 验收：两项 `test_q7_failed_*_rebuild_preserves_last_good_projection` 转绿；候选失败后旧数据、版本、去重状态均保留；成功后新数据可见。重复事件、乱序更新、删除后旧事件不复活以及当前主链失败别名测试继续通过。
- 完成标准：关闭夹具范围 F07；生产数据规模、真实服务可用性不随之自动签收。

## Q8：上传文件有合法文件头，就能交给模型吗？

**F08 根因：** 两种媒体存储的上传入口只看签名，头部截断 PNG、JPEG、WAV 仍以 201 入库。当前 WAV 在模型入口被拒绝，不能把上传缺口写成已成功利用的模型调用或代码执行。

- 公共边界：[media.py](../../apps/api/src/ragcommerce_api/media.py) 让内存与 MinIO 存储在写入前使用同一个内容校验函数；继续先检查 8 MiB 图片/25 MiB 音频上限。明确错误码：过大 413、不支持类型 415、内容损坏 422；失败无对象写入。
- 图片：为现有 PNG/JPEG/WebP 增加一个直接解码依赖 Pillow 并同步 `pyproject.toml`/`uv.lock`。检查实际格式与声明 MIME 一致；先验证结构，再重新打开并加载像素，拒绝截断和解码错误。项目默认只接收单帧、最多 1600 万像素，保留解压炸弹检查；这是项目入站策略，不宣称模型官方限额。
- 音频：按现有模型消费者实际支持的 PCM WAV 接受，读取帧数据验证非空和声明帧长一致，并前移现有 16 kHz、单声道、16 bit、最长 60 秒限制。当前仅凭头部接受但无对应消费者的 MPEG/OGG，在此修复中明确收窄为 415，同时更新公开类型声明及测试，不新增转码平台。
- 测试联动：[test_turn_api.py](../../apps/api/tests/test_turn_api.py) 中用 PNG/Ogg 假头充当正样本的夹具替换成有效媒体。保留 [test_media_flow.py](../../apps/api/tests/test_media_flow.py) 的所有者、过期与读取验证。
- 验收：三种头部截断输入在上传时拒绝；有效图片和 PCM WAV 正常；增加一个头部合法但解码损坏的图片、像素超限图和帧数据短缺的 WAV。拒绝路径对内存与 MinIO 适配器均证明无写入，且没有模型请求；类型收窄有明确 415 对照。
- 完成标准：关闭上传有效性 F08；MinIO 真实服务和真实语音理解仍按各自层级验证。Pillow 的 `verify()` 本身不解码，需重新打开后加载像素，见 [Pillow 文档](https://pillow.readthedocs.io/en/stable/reference/Image.html#PIL.Image.Image.verify)；WAV 帧读取依据 [Python wave 文档](https://docs.python.org/3.12/library/wave.html)。

## Q9：域名白名单能否覆盖 DNS 与跳转风险？

**F09 条件边界：** `resolved_addresses=None` 会跳过解析地址校验；当前离线夹具确实不做 DNS。省略参数已复现，但没有启用 LIVE 连接器，也未证明真实 SSRF 攻击成功。

- 严格入口：[connectors/security.py](../../packages/connectors/src/ragcommerce_connectors/security.py) 的默认校验要求每一跳都有非空解析地址，省略、缺键、空集合或包含非公网地址均拒绝。保留 HTTPS、默认端口、凭据禁止、精确主机白名单等现有约束。
- 离线入口：为现有本地夹具提供名称明确的 URL-only 校验方法，调用处显式改用它；不通过默认参数或失败 fallback 隐式降级。该方法不导出为 LIVE 安全保证。
- 接入要求：将来 LIVE 调用者逐跳解析并校验，实际连接目标必须绑定到已检查地址，TLS 仍校验原始主机名；每次重定向重新执行相同边界。仅“先解析，再让 HTTP 客户端另行解析连接”不能关闭 DNS 重绑定风险。
- 验收：`test_q9_omitting_dns_argument_cannot_skip_the_live_address_check` 转绿；现有公网正对照和混合私网负对照保留；增加严格入口与离线入口的调用隔离测试。真实接入时再验证解析变化和重定向下的实际连接目标，不在本任务开启联盟连接器。
- 完成标准：本地严格接口修复可以单独完成；F09 的 LIVE 门禁只有调用链和实际传输目标共同验证后才能关闭。依据 [OWASP SSRF 防护建议](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)。

## Q10：删除成功后，后台任务还能把数据写回来吗？

**F10 根因：** 删除与运行状态缺少同一所有者范围的同步。内存 API 已复现删除返回 200 后，仍在执行的任务再次 `save()`，重建孤立 checkpoint；PostgreSQL/MinIO 的同类竞态尚未实测。

- 默认语义：不新增即时取消状态机。有 `PENDING`、`RETRY`、`RUNNING` 任务时，删除返回 **409 busy**，不修改数据库或媒体；任务收尾完成后用户可重试。等待审批/澄清但没有执行中的任务可以删除，并同时清除其待续状态。
- 同步边界：[service.py](../../apps/api/src/ragcommerce_api/service.py)、[postgres_index.py](../../apps/api/src/ragcommerce_api/postgres_index.py)、[app.py](../../apps/api/src/ragcommerce_api/app.py) 用同一用户级互斥串行化任务登记、审批恢复和“检查活跃任务→删除”。任务在释放登记锁前必须成为可见活跃记录，终态只能在最后一次持久写入后标记；不能把租约超时直接当成旧执行者已停止。
- 两种适配器：内存使用所有者锁；持久层使用所有者键对应的 PostgreSQL 事务锁，检查和 SQL 删除复用同一个连接/事务。不能只加一个与写入不共用的锁，也不能依靠现有 mission 锁在其他连接上的持有来声称原子性。
- 清理顺序：[erasure.py](../../apps/api/src/ragcommerce_api/erasure.py) 的所有清理组件都必须在 busy 检查之后运行。梳理实际外键及用户关联数据，覆盖 checkpoint、事件、run、线程、偏好和媒体；不能从内存测试推断数据库级联完整。MinIO 删除按现有对象标识幂等执行，任何未完成清理均不得返回 `deleted=true`；跨 SQL/对象存储不宣称具有单一事务回滚。
- 与 Q4 联动：成功删除时撤销旧安装凭据；排队进入互斥区的请求须在区内重新确认所有者/凭据有效。旧 run/线程不存在时不能重新写出 checkpoint；新安装只生成新所有者，不让旧凭据恢复原数据。
- 验收：保留现有受控暂停用例，必须得到“运行中 409 且数据未改，完成后重试 200”；再覆盖删除先获得锁、同时新建任务或审批恢复的竞争。200 后释放旧执行者也不能恢复旧 checkpoint；其他所有者不受影响，重复删除符合约定，eraser 异常不假报成功。
- 持久化验收：用实际 PostgreSQL/MinIO 对两个服务/worker 实例复现同类交错，检查 409 前无对象清理、200 后关联数据及媒体均不存在，失败后的重试能收尾。只有内存测试通过时，将 F10 记为“本地已修复，持久化待验”，不能整体关闭。
