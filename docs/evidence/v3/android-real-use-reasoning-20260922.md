# V3 Android 真实使用推理验收

日期：2026-09-22  
设备：Pixel_9(AVD)-15，`emulator-5554`  
方式：ADB 依据 UI hierarchy 坐标点击/滑动，截图与 XML 同步留证；补充现有 Compose/领域测试结果。  
范围：从用户意图、前端按钮和视觉反馈判断本软件是否真正完成该意图。

## 总结结论

当前版本可以完成“提出一个购买任务 → Agent 返回带证据的演示候选 → 纵向浏览主/次推荐 → 用户确认保存或加入待购计划 → 进程重启后恢复任务进度”的演示闭环。

它还不是可完成真实购买的电商导购：报价是 `DEMO_FIXTURE`，不会下单或支付；真实商家库存、实时价格、规格变体、购物车结算和售后均不在能力边界内。

按用户意图分层：

- **可直接实现**：商品发现、约束驱动推荐、候选浏览、保存候选、加入待购计划、恢复任务。
- **部分实现**：信息不完整时的澄清、比较工作台、报价变化/过期、商家跳转、离线恢复；这些已有实现和自动化覆盖，但本轮未全部在同一条 ADB 业务链上完成。
- **不能实现**：真实市场购买承诺、真实支付、订单/物流/退款、联盟 LIVE 报价，以及可验证的真实库存。

## 视觉与操作缺陷

### P0：业务语义边界（不是代码崩溃）

1. **演示数据边界已前置到价格、商家和动作层**：`DEMO_FIXTURE` 显示“演示报价 · 不可作为成交价”“演示商家”和“查看演示来源”，不再使用“前往商家”的成交语义；LIVE、第三方核验和发现线索分别显示各自证据等级。
2. **五类商业事实已拆分**：价格、库存、配送、商家、售后均由接口返回独立 `BusinessFact`；Android 不再从一个报价状态推断库存、正品或售后能力。真实联盟和平台事实仍是外部门禁。
3. **用户意图没有覆盖交易闭环**：加入待购的确认面板已经说明不会下单，这是正确的边界，但产品名称和按钮仍容易让非技术用户期待真实购买。

### P1：交互语义

1. **比较选择已收口**：Agent 返回的 comparison 事件不再改变用户选择；候选默认不选，用户选择持久化到线程并随快照恢复。决策页提供横向事实表及预算、硬约束、偏好排序。
2. **任务恢复导航已收口**：`CHECKING/RECONNECTING/RECOVERED` 状态强制回到任务页并禁用底部切页；恢复页只保留“继续任务”主操作，确认后切换为 `ONLINE` 并重新开放导航。
3. **音频入口未形成闭环证据**：图片入口能打开系统选择器；音频按钮在恢复态不可直接触达，本轮无法证明从录音到 Agent 解析完成。
4. **结构化 Mission 与 Android 编辑已收口**：服务端从同一事件链返回商品项、硬约束、软偏好、待澄清字段和总预算；`POST /v1/missions/parse`、`mission_updated` 与 `ThreadSnapshot` 契约一致。任务页和推荐页展示可横向浏览的约束条；编辑后不会自动覆盖推荐，只有用户点击“重新计算推荐”才持久化新版本并重新运行 Agent。

### P2：信息与视觉层级

1. `Aural%20Audio%20Quiet%2001` 在截图中以 URL 编码形式展示，属于明显的用户不可读文本，应解码为空格。
2. “理解需求 / 混合检索 / 核验证据 / 比较候选”执行阶段视觉冲击很强，但对普通用户的帮助有限；应在完成后折叠为“已完成的工作”摘要，把空间让给约束和推荐理由。
3. 主推荐和次推荐卡片高度很大，单屏只能看一张；这符合纵向叙事，但比较多个候选的效率较低，决策页需要真正的横向对比表而不是再次堆叠卡片。

## 复杂电商业务目的推理

以下场景按照淘宝、京东等一线购物软件的真实使用习惯补充。它们不是“再加几个按钮”，而是用户会同时提出的复合目标；判断标准是 Agent 能否理解目标、管理约束、调用工具并让用户完成可验证的结果。

| 复杂目的 | 用户真实说法 | 需要的 Agent 推理与业务动作 | 当前判断 |
|---|---|---|---|
| 多件套一次买齐 | “给我配一套预算 5000 的办公桌面：显示器、键盘、鼠标和耳机，不能重复功能。” | 拆解子任务；分配总预算；处理品类依赖；联合检索；去重；给出整套与单项替代方案 | **部分实现**：当前 Mission 是单任务单候选流，没有可见的购物清单编排和跨品类预算求解 |
| 家庭/团队采购 | “给 3 个家人买不同尺寸的运动鞋，预算 2000，周末前送到。” | 识别多个收货人；按人分配规格；合并/拆分订单；校验库存和时效 | **不支持**：无收货人、尺码矩阵、地址和配送时效状态 |
| 预算有优先级 | “总预算 3000，降噪必须最好，外观可以妥协，不能超过 1500。” | 区分硬约束/软偏好；对冲预算；解释牺牲了什么；提供超预算和降级方案 | **部分实现**：结构化硬/软约束可编辑；严格、预算、替代路线分别显示超预算、放宽偏好或改变硬约束，但尚未完成多商品预算分配 |
| 规格变体选择 | “买 16GB/1TB 的笔记本，银色，国行，不要无货版本。” | 识别 SKU 变体；过滤库存；比较同款不同规格价格；锁定最终变体 | **不支持**：当前卡片是规范化商品，不展示可选规格、库存和变体级报价 |
| 价格与促销最优 | “今晚买最便宜，能叠加学生券和满减，会员价也算进去。” | 读取券规则、门槛、会员身份、时间窗；计算到手价；避免把标价当成交价 | **不支持**：只有演示报价，没有券、会员、满减和有效期计算 |
| 送达时限 | “明天下午前送到公司，不能放驿站。” | 根据地址、仓库、配送方式和截单时间判断承诺；不能满足时给替代 | **不支持**：没有真实地址、库存、仓配和配送承诺工具 |
| 正品与售后 | “只要官方旗舰店或自营，支持 7 天无理由和全国联保。” | 过滤商家资质；验证授权/发票/售后条款；把商业证据挂到商品 | **不支持真实验证**：界面可展示来源字段，但演示商家不构成正品或售后证明 |
| 对比后做决定 | “比较这 3 款，告诉我哪款最适合通勤，并说明放弃了什么。” | 统一维度对齐；识别冲突指标；解释推荐理由；允许用户改变权重后重排 | **部分实现**：有比较入口和理由字段，但当前比较勾选疑似默认全选，缺少可见权重调节 |
| 价格追踪与降价提醒 | “现在先别买，低于 800 通知我。” | 创建价格观察任务；保存阈值；定期重新询价；通知并保留历史证据 | **演示草稿**：阈值与补货观察可持久化并恢复，但固定显示“不会后台提醒”；调度器和通知渠道尚未实现，因此不冒充可用提醒 |
| 缺货替代 | “这款没货就换同价位、同接口、续航不低于 20 小时的型号。” | 明确替代优先级；重新检索；保持硬约束；标记替代原因 | **部分实现**：替代路线绑定不同商品或规格并明确列出放宽项；真实缺货触发仍受外部库存数据门禁限制 |
| 退换货决策 | “我担心不合适，先比较退货成本和试用政策。” | 读取平台/商家退换条款；计算运费和时间成本；提示不可退条件 | **不支持**：没有售后规则工具和订单上下文 |
| 跨平台比价 | “淘宝、京东、拼多多都搜一下，选到手价最低且售后最稳的。” | 多渠道检索；统一商品实体；比较到手价、配送、售后和可信度 | **不支持**：当前数据源是项目自有演示数据，不连接平台联盟或公开报价 API |
| 购物车/结算 | “把选中的 2 件加入购物车，地址用默认地址，提交前让我确认。” | 批量写入；校验库存、优惠、地址；审批后创建订单 | **不支持**：待购计划不是购物车；没有订单和支付写操作 |
| 复购 | “按上次买的型号再来两件，但价格涨 10% 就换同级。” | 查询历史订单；识别同款；比较涨幅；替代推荐 | **不支持**：没有真实订单、用户历史和复购任务 |
| 礼物场景 | “给不懂数码的父亲买手机，预算 2500，周五前到，包装要体面。” | 从关系/场景推断偏好；追问关键限制；考虑礼品包装和时效 | **部分实现**：能理解自然语言场景，但礼品包装、收货人和时效不可执行 |
| 账号与权限 | “家人可以看推荐，但不能替我加入待购或跳转商家。” | 区分查看、写入、外跳权限；每次高风险动作审批 | **部分实现**：当前有审批边界，但没有真实家庭成员、角色和权限管理 |

### 复杂推理的关键缺口

当前 Agent 更像“单次购买决策器”，而一线电商用户经常需要的是“任务编排器”：

1. **缺少任务分解**：不能把一段话拆成多个商品、多个收货人和多个约束。
2. **缺少状态化购物清单**：待购计划不是可计算的购物车，不能做数量、规格、预算和库存联动。
3. **缺少交易事实层**：券、会员、库存、地址、配送、售后、订单都没有真实数据源。
4. **持续任务仅有草稿层**：降价与补货条件可持久化，但没有调度器、通知渠道、复购历史或价格时间序列，界面明确不声称后台运行。
5. **决策编辑仍有限**：用户可以编辑整句约束并明确重新计算，也能查看三路线取舍；尚无逐项权重控件和跨商品预算求解器。

因此，若把目标定义为“像淘宝/京东一样完成购物”，当前完成度约为 **30%—40%**；若目标定义为“有证据、有审批边界的演示型购买决策 Agent”，当前核心链路约为 **70%**。后一个比例不代表真实商业可用率，只代表现有演示范围内的用户任务完成度。

## 最终判断

本软件当前能满足“让 Agent 帮我做购买决策”的核心意图，且真实可操作闭环已经成立；不能满足“像淘宝一样直接买东西”的意图。更准确的产品定位是：**带证据和审批边界的 RAG 电商决策 Agent 演示**，而不是完整电商平台。

本轮没有修改业务代码、没有删除用户文件、没有提交或推送。`07-again.xml/png` 因被 `com.catlife.mvp` 抢占前台而标记为无效证据，未用于通过结论。

证据目录：`output/adb-reasoning-20260922/`。关键文件：`01-first-use.*`、`02-image-picker.*`、`03-recommendation.*`、`04-cancel-waiting.xml`、`05-after-confirm.*`、`06-secondary.*`、`08-decisions-screen.*`。
