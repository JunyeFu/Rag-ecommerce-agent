# 架构设计

> 评委问："为什么选这些技术？架构怎么设计的？" → 此页

## 三层架构总览

```
Android (Kotlin Compose, 24 Screen, 73 .kt)
  │  SSE (OkHttp EventSource)
  ▼
FastAPI :8080 (API 路由 + services 分层)
  │
  ├── LangGraph Agent (7 个显式主节点 + 条件路由)
  ├── Qdrant (1024-dim 向量检索 + BGE Reranker)
  └── PostgreSQL (商品/购物车/订单/会话 持久化)
```

## 技术选型与理由

| 层 | 选型 | 为什么不用替代方案 |
|----|------|-------------------|
| Agent 编排 | **LangGraph StateGraph** | LangChain 无状态图原生支持；LlamaIndex 偏检索不偏编排 |
| 向量库 | **Qdrant** (自部署) | Milvus 资源重，Chroma 不适合生产，pgvector 慢于专用库 |
| 后端 | **FastAPI** (async) | 原生 SSE EventSourceResponse；Gin/Express 非 Python 生态 |
| LLM | **Doubao-Seed-2.0-lite** | 比赛提供 Key，TPM 800K + RPM 700 |
| Embedding | **BGE-large-zh-v1.5** | 中文电商领域 SOTA，本地部署无 API 依赖 |
| Reranker | **BGE-Reranker-v2-m3** | 中文 Cross-Encoder 精排，与 BGE Embedding 同生态 |
| 前端 | **Kotlin + Jetpack Compose** | 比赛要求原生，非 H5/WebView |

## Agent 编排（7 个显式主节点 + 条件路由）

```
classify_intent ──→ route_after_intent
  ├── retrieve → rerank → product_ranker → generate (推荐/场景/反选)
  ├── compare → generate (多商品对比)
  ├── clarify → generate (缺失信息追问)
  ├── cart → generate (购物车 CRUD + 下单)
  ├── web_search → generate (外部信息兜底)
  └── generate (闲聊引导)
```

## 关键架构决策

### 1. 双库协同
- PostgreSQL 存储结构化数据（商品/购物车/订单/会话）
- Qdrant 存储向量 + payload（JSON），通过 UUID5 确定性 ID 双库同步
- 避免跨库 ID 映射不一致

### 2. SSE 交错流式
- 8 种自定义事件类型（progress/text_delta/product_cards/clarify/compare/cart_update/scenario/done）
- LLM 输出结构化标记 `[SUMMARY]` / `[PRODUCT_N]` / `[CLOSING]`
- 后端解析后按「摘要 → (商品文本 + 卡片) × N → 结语」交替推送

### 3. 全栈数据契约
- `docs/standards/DATA-CONTRACT.md` 定义 ProductRecord 统一模型
- Qdrant payload → Pydantic Schema → SSE event → Kotlin data class 全链路字段对齐
- 消除字段名不一致（image_urls ↔ imageUrl）

### 4. 多轮状态管理
- PostgreSQL `sessions` 表持久化对话状态
- 对话历史品类继承 + 切换品类自动重置偏好
- 缓存 key 含 conversation_id 实现多轮上下文感知
